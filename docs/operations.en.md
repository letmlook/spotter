# Operations Guide

This document covers what an operator needs to do **after** Spotter has
been deployed: lifecycle, configuration, log locations, and routine
maintenance. For the install steps see `README.md`.

## Component summary

| Component       | Process                          | Lives on                    |
| --------------- | -------------------------------- | --------------------------- |
| `spotterd`      | systemd unit (`spotterd.service`)| each managed Linux device   |
| `spotter-client`| Wails desktop app                | operator's macOS / Windows / Linux |
| Registry        | `<UserConfig>/Spotter/devices.json` | client host only         |
| Agent config    | `/etc/spotterd/agent.toml`       | each device                 |

## Filesystem layout on a managed device

```
/usr/local/bin/spotterd              # the agent binary, mode 0755
/etc/systemd/system/spotterd.service # systemd unit, mode 0644
/etc/spotterd/                       # agent config dir, mode 0755
    └── agent.toml                   # device_id, listen_addr, multicast
/var/log/journal/                    # spotterd logs land here (journald)
```

`ssh user@device sudo systemctl status spotterd` is the canonical health
check. To inspect live logs:

```bash
ssh user@device journalctl -u spotterd -f
```

## Filesystem layout on the client host

| OS      | Path                                                           |
| ------- | -------------------------------------------------------------- |
| macOS   | `~/Library/Application Support/Spotter/devices.json`           |
|         | `~/Library/Application Support/Spotter/logs/spotter.log`        |
| Linux   | `~/.config/Spotter/devices.json`                               |
|         | `~/.config/Spotter/logs/spotter.log`                          |
| Windows | `%APPDATA%\Spotter\devices.json`                               |
|         | `%APPDATA%\Spotter\logs\spotter.log`                           |

## Configuration

### Agent (`/etc/spotterd/agent.toml`)

```toml
device_id        = "9d1f2c5e-…"     # UUID v4 generated by install.sh
listen_addr      = "0.0.0.0:9999"   # bind interface & port
multicast_group  = "239.255.42.42:9999"  # discovery group
agent_version    = "0.1.0"          # stamped by install.sh
hello_interval   = "5s"             # proactive HELLO cadence; missing/0 → 5s
```

On by default: `enable_power_actions = true` enables GUI-driven remote power actions; to turn it off, explicitly set `enable_power_actions = false` in `agent.toml`.

On by default: `enable_log_stream = true` enables GUI live-log streaming (combine with `log_unit` to point at a different systemd unit); to turn it off, explicitly set `enable_log_stream = false` in `agent.toml`.

`hello_interval` controls how often the agent broadcasts HELLO on the
multicast group. The client listens for these HELLOs and immediately
marks a registered device as online — this path bypasses HTTP polling,
so a device coming back shows up in the GUI within one mcast interval
plus one RTT. Lowering `hello_interval` (minimum recommended 1s) trades
extra multicast traffic for snappier online detection; the 5s default
is fine for typical LANs.

To change the listen port after install:

```bash
ssh user@device sudo sed -i 's/listen_addr = "0.0.0.0:9999"/listen_addr = "0.0.0.0:9100"/' /etc/spotterd/agent.toml
ssh user@device sudo systemctl restart spotterd
```

The multicast group is set at install time. Changing it requires editing
the unit file too — easier to re-run `scripts/install.sh` with the new
`MULTICAST_GROUP` env var.

### Client registry (`devices.json`)

Plain JSON, readable while the client is closed. Two safe edits:

- Delete an entry to force re-discovery of that device (the next 30 s
  poll cycle will recreate it).
- Move the file aside to "start fresh" — the GUI rebuilds the registry
  from the next multicast / probe cycle.

Do not edit `LastInfo` in place; the client overwrites it on every poll.

## Routine tasks

### Rolling restart of a device

```bash
ssh user@device sudo systemctl restart spotterd
```

The client marks the row as offline within ~30 s (one missed poll), then
green again on the next successful poll. This is expected behavior.

### Re-pinning a device that moved networks

If a device migrated to a new subnet (new DHCP lease, new VLAN):

1. In the client, remove the stale entry from the registry.
2. The 30 s poll will fail; the row shows offline.
3. Re-add the device by IP (Add Device by IP) — the client prefers a
   freshly-probed entry over a stale registry one.

Or: just rerun `scripts/deploy.sh` so the device picks up the new
`/etc/spotterd/agent.toml` and the GUI re-discovers it under its new IP.

### Bumping the wire protocol version

Wire format changes go through the `schema_version` field in
`internal/protocol/info.go`. Bump it together with the major version in
`wails.json` (client) and `agent_version` in the install script
(`scripts/install.sh`). The protocol package ships its own test for
backwards-compat decoding.

### Uninstalling

On a device:

```bash
sudo bash /tmp/uninstall.sh        # stops & removes service only
sudo bash /tmp/cleanup.sh         # also wipes config + /tmp scratch
```

On the client: use **Tools → Clear Registry**, or quit the app and
delete `<UserConfig>/Spotter/`.

## Upgrade strategy

Spotter is pre-1.0; minor versions may include breaking changes to the
wire protocol. Plan device upgrades in lockstep with the client:

1. Cut a release tag (`git tag v0.2.0`).
2. The GitHub Actions release workflow builds Linux arm64/amd64 binaries.
3. Re-run `scripts/deploy.sh` against each device to push the new binary.
4. Update the client (the auto-update story is not implemented — users
   grab a binary from the GitHub release).

For multi-VLAN deployments, do (3) device-by-device to keep blast radius
small.

## Observability

There is no central aggregator in 0.1.0. The simplest path is to ship
`journalctl -u spotterd` to a log forwarder you already run (Promtail /
Vector / fluent-bit). The agent emits `slog` JSON to stderr, which
journald captures in one line per record.
